Marrying firstmate and agent-box

Goal: run the whole first-mate crew inside Docker on your Windows machine, with no WSL and no native-Windows workarounds. This page is a plan for you to react to. Nothing here has been built yet.

The core idea. Firstmate is built for Linux and macOS, and its Windows port is the part that keeps breaking (the lock failure you hit this morning came from exactly that). A Linux container is the platform firstmate was written for. So: build one Linux image that has agent-box's tools plus firstmate's tools, and run the first mate and every worker inside it, each worker as a tmux window.

1. What we have today

agent-box works

  • Docker image: Node 22, git, pnpm, uv, Claude Code, pi (versions pinned).
  • docagent cc|pi starts one interactive agent, then the container is thrown away (--rm).
  • Projects are bind-mounted from D:\Code. Login and package caches live in named volumes.
  • No git credentials, no gh, no tmux in the image.

firstmate needs more

  • Needs a long-lived session: a watcher process, a session lock, tmux windows for each worker.
  • Required tools: bash, git, node, gh (logged in), tmux, treehouse, no-mistakes, jq, and the axi tools (gh-axi, tasks-axi, quota-axi, chrome-devtools-axi, lavish-axi).
  • Keeps private state (data/ state/ config/ projects/) in one folder.
  • Needs to push branches and open PRs, so it needs a GitHub token.

The mismatch is simple: agent-box is "one short-lived agent per command", firstmate is "one long-lived container that supervises many agents". The plan below turns agent-box into the second shape without throwing away the first.

2. Target picture

Arrows: launcher attaches you to tmux; Lavish pages are published from the container on port 4387 to your browser; the dashed link is the optional Windows bind mount; the container reads and writes the named volumes. The container also reaches GitHub (push, PRs) and Anthropic (your Claude subscription) over the network.

Is it Linux or Windows inside Docker, and where is WSL? Inside the container it is always Linux (Debian). Docker Desktop on Windows runs a small hidden Linux virtual machine to host Linux containers, using WSL 2 or Hyper-V as its own plumbing. That is outside our setup and you never touch it. "No WSL" in agent-box means you do not install or use a WSL distro (such as Ubuntu) yourself. Your Windows folder D:\Code is outside Docker; keeping projects in a Docker volume avoids the slow Windows-to-Linux file translation. You still type docagent ... in PowerShell; everything after that runs in Linux.

1

Build the image: add firstmate's tools to agent-box

A second Dockerfile that starts FROM agent-box (so Claude Code, pi, Node, pnpm and uv stay exactly as pinned) and adds:

  • apt: tmux jq procps bash unzip (procps matters: firstmate finds its session by walking process ancestry, which is what failed on Windows).
  • gh, treehouse and no-mistakes as pinned Linux release binaries.
  • npm: gh-axi tasks-axi quota-axi lavish-axi chrome-devtools-axi, pinned like the others.
  • The firstmate repo cloned into /opt/firstmate (your fork, so your Windows fixes are not lost).

Browser for chrome-devtools-axi is optional; firstmate lists it as required, so we either install Chromium or accept its warning. Needs a quick test.

Who: a worker in the agent-box repo.

I suggestPin every version, as agent-box already does. Build it as a second layer on top of the existing image so nothing there changes.
You'll know it workeddocker build finishes, and tmux -V, gh --version and treehouse --version each print a version inside the container.
2

Make the container long-lived

In plain words. Today, docagent cc works like opening a program: you type it, a container starts, you chat with one agent, and when you quit, the container is deleted. That is fine for one chat.
Firstmate is different. It is a team lead that has to keep watching its workers for hours: it waits for them to finish, notices when one gets stuck, and remembers who is doing what. If the container disappeared whenever you closed the terminal window, the team lead would vanish and every worker would be killed with it.
So the container runs in the background, like a small always-on computer. Closing your terminal only closes your view of it. The work carries on inside. Next time you type docagent fm, you reconnect to the same running session, the way you reopen a laptop lid. (A reboot or "docker stop" does stop it; state is kept in volumes, so it picks up from disk.)

How do I actually stop it?

You want to...Do thisWhat happens
Just leave for nowClose the terminal, or press Ctrl+B then DNothing stops. Workers keep going.
Pause everything (keep all work)docagent fm stop (= docker stop firstmate-box)The container, first mate and workers stop. Volumes keep every file, login and backlog. docagent fm start brings it back and the first mate picks up from disk.
Shut down tidilyAsk the first mate to wrap up first, then docagent fm stopWorkers finish or park cleanly, so nothing is cut off mid-task.
Remove the box, keep your datadocker rm firstmate-box after stoppingThe container is deleted; volumes stay. Starting again recreates it.
Erase everythingdocker volume rm on the fm volumesPermanent: state, clones and logins are gone. Only on purpose.

It also uses no CPU while idle, and --restart unless-stopped means it comes back after a reboot unless you stopped it yourself, so a stop stays a stop.

Today docagent uses docker run -it --rm. For firstmate the container must stay up when you close the terminal:

docker run -d --name firstmate-box --restart unless-stopped `
  -v fm-home:/home/node/fm -v fm-projects:/home/node/fm/projects `
  -v agent-box-claude:/home/node/.claude -v agent-box-pi:/home/node/.pi `
  -v fm-gh:/home/node/.config/gh -p 127.0.0.1:4387:4387 `
  firstmate-box  tmux new -d -s firstmate 'claude' ; sleep infinity

Then docagent fm is just docker exec -it firstmate-box tmux attach -t firstmate. Ordinary docagent cc and docagent pi keep working unchanged.

Who: a worker, then a quick check by you.

I suggest--restart unless-stopped, and publish port 4387 on 127.0.0.1 only so nothing outside your PC can reach it.
You'll know it workedClose the terminal, run docagent fm, and you are back in the same session with workers still running.

6. Decisions for you

A. Where do projects live?

  • Docker volume recommended: fastest, hard links, about 67% less disk, no Windows file-sharing slowness. Files are not visible in Explorer.
  • Stay on D:\Code: you can open files in any Windows tool, but builds are slower and the disk saving stays near 12%. Git worktrees across the Windows/Linux boundary are also fragile.

B. How does it reach GitHub?

  • Fine-grained token in a volume recommended: simplest, limited to the repos you pick.
  • SSH agent forwarding: keys never enter the box, but Windows-to-container forwarding is awkward without WSL.
  • No push from the box: it works only on local branches; you push by hand. Breaks the PR flow.

C. Scope of the first build

  • Smallest first recommended: phases 0 to 5 with one project, then widen.
  • Everything at once: all projects and polish in one go. More to debug if phase 5 fails.
Where I would start. Say "a, a, a" (volume, token, smallest first) and I will queue the image build as a task for a worker in the agent-box repo, with phase 5 as its acceptance test.
